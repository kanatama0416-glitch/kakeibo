# kakeibo

同棲用の「ふたり家計」Webアプリです。

## 現在の構成

- GitHub Pages で配信する静的フロントエンド
- Supabase Auth + RLS で許可されたユーザーだけが家計データへアクセス
- 支出の手入力・全項目編集・削除
- エポス / 楽天カードの PDF・CSV 明細取込
- カード取込ごとの履歴（取込者・日時・対象月・カード・件数・金額）と明細の出自追跡
- 未仕分け明細の確認、自動分類ルール、「毎回確認」ルール
- 月次精算、翌月繰越、立替金と返済
- 個人間の立替（その月の精算で全額清算）
- 返金・取消をマイナス金額で記録
- 操作した人と日時を含む変更履歴
- 月別 / 費目別の分析

## 運用ルール

- 家計運用開始月は **2026年10月**。
- 返済も **2026年10月分から**開始する。
- 運用開始前（2026年9月以前）の利用分もカード明細から取り込める。ただし精算は2026年10月分から。
- 自動分類ルールがないカード明細は「未仕分け」で保存し（DB上は `status = 'unclassified'`）、仕分け後に精算額へ反映する。画面上の呼び方は「未仕分け」に統一する（費目だけがない仕分け済みの明細は「費目なし」）。
- 共用カードはなく、個人カードで共同費も払う。明細画面では取り込んだ明細を「共同」か「対象外（個人の買い物）」に仕分ける。対象外は精算・集計に含めず、個人支出の管理はしない（DB上は支払者に合わせて mine / partner で保存）。
- 支出の入力は「払った人」「誰の分？（ふたり / うーの分 / にゃちの分）」「分け方（いつもの割合 / 金額で分ける）」のボタンで選ぶ（`split-editor.js`、計算は `lib/split.js`）。払った人と別の人の分 = 立替、払った人自身の分 = 対象外。
- 「ふたり・金額で分ける」は `transactions.me_share_amount`（にゃちの負担額）に保存し、その額で精算する。生活費の合計・使い道には支出額の全額が入る。いつもの割合の分は従来どおり月の合計で丸める。店舗ルールには保存しない。
- 個人間の立替（例：にゃちが うーの分を払った）は、誰の分？で相手を選んで登録する（DB上は `scope = 'advance'`、支払った人 = 立て替えた人）。その月の精算に全額を反映し、共同費の合計・負担額・使い道/分析には含めない。店舗ルールには保存しない。長期で返していく立替金（立替・返済画面）とは別物。
- 店舗ルールが「毎回確認」の明細も自動確定せず、未仕分けで保存する。
- **その月の分はその月末に精算する**（例：10月分を10月末に）。当月分から精算済みにでき、未来月は不可。
- 明細は「利用日（分析・明細一覧の月）」と「精算月（`transactions.settlement_month`、お金の月）」を別に持つ。精算月は DB のトリガーが決め、画面からは変えられない。ふだんは利用日の月、**精算済みの月の利用分を後から追加・取込したときは次の未精算月**になる（例：10月を精算した後に届いた10月分のカード明細は11月の精算に入り、分析は10月のまま）。明細一覧では「11月精算」の目印、精算内訳では「うち前月までの追加分」で分かる。
- 精算済みの月の精算に入った明細の金額・日付・支払者・支出区分・分け方と、その月の繰越・返済額はロックする。修正するときは、先にその月の画面から「支払いを取り消す」。取り消しても、後から次月の精算に入った明細は次月のまま。
- 精算済み履歴がある状態では共同費の基本負担率を変更しない。
- **明細 ⇄ 立替金の移動**：明細の編集画面「立替金（毎月返す）に移す」で明細を立替金に、立替金の編集画面「通常の支出に戻す」で費目と分け方を選んで明細に戻せる（`lib/move-expense.js`・`move-expense-dialogs.js`）。DB は1件ずつ変えるので「移す先を作る → 元を消す」の順に行い、元を消せなかったら作った方を消して戻す（それも失敗したら、両方残ったことを画面で知らせる）。精算済みの月の精算に入った明細・返済済みの額を下回る立替金は、既存のロックのとおり移せない。返金（マイナス）の明細は移せない。カード取込の明細を移した後に同じ明細ファイルを取り込み直すと、新しい明細として入り直す（確認画面で注意を出す）。運用開始前の日付の立替金を明細に戻すと精算に入らないので、確認を出す。その月に清算する「立替」と通常の切り替えは、編集画面の「誰の分？」で行う。
- **毎月の固定費**（設定 →「毎月の固定費」）：家賃など毎月同じ額の支出を登録すると、開始月〜今月の各月に「毎月◯日」の日付で支出を1件ずつ自動で入れる（DB の `public.kakeibo_generate_recurring_expenses()`、アプリを開いたとき・固定費を保存したときに呼ぶ。月の数え方は `lib/recurring.js` と同じ）。月にない日（31日など）は月末。アプリを開かなかった月の分も次に開いたときに入る。同じ固定費・同じ月は `transactions (recurring_expense_id, recurring_month)` の一意制約で1件だけ。入れ終わった月は `recurring_expenses.last_generated_month` に残すので、1か月分を手で消しても入り直さない。内容の変更は次に入れる月から反映し、入れ済みの明細は変えない。一時停止から再開した月より前はさかのぼらない。固定費は「ふたり」か「立替」だけ（個人の分は不可）。カードで払う固定費は明細取込で入るので登録しない。
- 楽天Gmail自動取込は廃止済み。カード明細は PDF / CSV から取り込む。
- 前月分のカード明細がまだ取り込まれていないカードは、ホームにリマインドを表示する（取込履歴の「何月分」で判定。前月を精算済みにしても、取り込むまで消えない）。
- 同じファイル内に同じ日・金額・利用先の明細が複数あるときは、別々の利用として両方登録する（登録済みの明細と一致するものだけ重複として外す）。
- 精算額は画面とDB（`private.kakeibo_settlement_breakdown`）の両方で計算し、一致しないときは精算済みにしない。
- **オフライン**：一度オンラインで開いた端末なら、オフラインでも起動して最後に読み込んだデータを表示する（`sw.js` が画面と部品を、`lib/offline.js` が家計データを端末に保存）。オフラインでできるのは閲覧と支出の追加だけ。追加した支出は端末に「未送信」として残り、通信が戻ると自動で送信する。編集・削除・仕分け・精算・取込・設定はオンライン時だけ。
- 支出の手入力は端末で発行した送信ID（`transactions.client_request_id`、一意）を付けて送る。同じ送信IDの再送は登録済みの1件を返すので、応答が届かず送り直しても二重登録にならない。
- DB に拒否された送信待ちは「送信エラー」として残り、アプリを開くたびに一度送り直す。未送信の支出がある間は精算済みにできない。ログアウトすると端末のデータと未送信の支出は消える。

## DB

本番DBは Supabase の migration を正とします。

現在は、RLS、監査ログ、月次精算RPC、精算済み月の更新ロック、立替金と返済計画の整合性維持をDB側でも行います。カード取込履歴は `cards` / `import_batches` と `transactions.card_id` / `transactions.import_batch_id` で管理します。

`supabase/schema.sql` は初期構築用の古いベースラインで、**schema.sql + migrations だけでは本番を再現できません**。次のオブジェクトは本番DBにだけ存在し、リポジトリに定義がありません。

- テーブル：`monthly_settlements` / `monthly_repayment_amounts` / `audit_logs`
- `repayments.repayment_month` 列と `(repayment_plan_id, repayment_month)` の一意制約
- 関数：`public.kakeibo_undo_settlement_paid`、監査ログ用トリガー関数

本番から現行スキーマを書き出して、ベースラインを置き換えてください（要 Supabase CLI・DBパスワード）。

```sh
supabase login
supabase link --project-ref vcokmkljwxuyiytiqtlc
supabase db dump --schema public,private -f supabase/schema.sql
```

書き出した後に `private.allowed_users` の実メールが含まれていないか確認してからコミットすること。

## コード構成

- `boot.js`：本番 / テスト環境の読み込みを切り替える
- `lib/core.js`・`lib/settlement.js`・`lib/split.js`・`lib/card-import.js`・`lib/recurring.js`：画面に依存しない計算と判定（精算額、繰越、返済、1件の分け方、取込の重複判定、取込状況、固定費を入れる月）
- `move-expense-dialogs.js`：明細 ⇄ 立替金を移す画面操作（処理は `lib/move-expense.js`）
- `recurring-settings.js`：設定 →「毎月の固定費」の画面（計算・入力チェックは `lib/recurring.js`）
- `split-editor.js`：払った人・誰の分？・分け方の入力部品（支出の追加・明細の編集で共通）
- `app.js`：画面の表示と操作
- `supabase-client.js`：DBへのアクセス（テスト環境では `test/test-db.js` が同じ関数を持つ）
- `test/unit/`：`lib/` の単体テスト（`node --test test/unit/*.test.js`）。GitHub Pages への公開前にも実行される

## メンバー（表示名）

「にゃち / うー」とメールアドレスの対応は `private.allowed_users` の `member_key`（me / partner）と `display_name` に持たせ、`public.kakeibo_members()` で読む。コードにメールアドレスを書かない。

## テスト画面

テスト環境は `index.html?mode=test`（`/test/` からも転送）。本番と同じ `index.html` を使い、`boot.js` が Supabase の代わりに `test/test-db.js` のダミーデータを読み込む。

## セキュリティ

ブラウザには Supabase publishable key だけを置き、secret / service_role key は置きません。

家計データは authenticated ユーザーに対する RLS と許可ユーザー一覧で保護します。
